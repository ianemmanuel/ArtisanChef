# DailyBread — Admin Platform

Turborepo monorepo for a multi-country food delivery platform's admin/ops tooling.

## Layout

- `apps/admin-dashboard` — Next.js (App Router) admin UI, Clerk auth
- `apps/backend` — Express API
- `packages/database` — Prisma schema + seed scripts (`@repo/db`)
- `packages/types` — shared types/enums, split into `domain/`, `backend/`, `frontend/` (`@repo/types/backend`, `@repo/types/admin-app`, `@repo/types/enums`)
- `packages/ui` — shared component library (shadcn-style, `@repo/ui/components/*`)

Type-check: `pnpm run check-types` per app (backend writes to `reports/typecheck/backend.txt`; empty file = clean).

**Super admin permission drift — found and fixed while validating this roadmap (2026-08-26).** Confirmed the mechanism directly: `create-super-admin.ts` only grants "the pool as it existed at creation time" and refuses to touch an already-`active` account; the in-app permission editor's `assertTargetNotSuperAdmin` refuses to edit *any* super_admin's permissions, always. Net effect — a super_admin account, once active, had no path (script or UI) to ever receive a permission added after it was created. Confirmed this wasn't hypothetical: running the fix against this dev database actually granted **9 missing permissions** to an existing super_admin account. Fixed with a new idempotent seed step, `syncSuperAdminPermissions()` (`packages/database/src/seed/admin/sync-super-admin-permissions.seed.ts`, step `[3/5]` in `seedAdmin()`) — grants every `super_admin`-role `AdminUser` any pool permission (`ROLE_POOLS.super_admin`, i.e. `ALL_PERMISSION_KEYS`) they don't already individually hold, every time `pnpm db:seed` runs. Verified idempotent (re-run reports 0). This is what actually makes "super admin sees every page" durable over time — nav items were already confirmed to be permission-gated with no hardcoded role checks anywhere in `admin-dashboard`, so once the individual grants are complete, every gated link renders correctly.

### Compliance case workflow refinement (2026-08-26, post-roadmap)

A user-directed rework of the claim/escalate/manage rules, done after P0-P2 were complete — not itself a numbered roadmap item, but load-bearing for anything that touches compliance cases going forward. Schema migration `20260826150000_add_compliance_case_refinements_and_admin_notifications`.

**New rules** (all enforced server-side, not just in the UI):
- **Claim required to manage.** Waiving, notifying, revoking a waiver, or reviewing a compliance-linked document now requires the actor to already be the case's claimed owner (`assertClaimedByActor`/`assertVendorDocumentReviewableByActor`, `admin.vendor.compliance-case.service.ts`) — previously `VENDORS_ACCOUNTS_COMPLIANCE_MANAGE` alone was enough regardless of who (if anyone) had claimed the case. No "unclaimed = anyone may act" fallback for these, unlike claim/escalate themselves.
- **Reassignment now exists for compliance cases** (`VENDORS_COMPLIANCE_REASSIGN`, `reassignComplianceCase`) — modeled on `reassignApplication`: a supervisory override that doesn't require ownership, transfers the case directly (status `CLAIMED`, no separate "accept" step for the target), narrower eligible-target pool when reassigning out of the open escalation pool (RECEIVE_ESCALATION holders only). New `GET /vendors/compliance/cases/eligible-targets` powers the target picker.
- **Terminal escalation rule.** `VendorComplianceCase.claimedFromEscalation` (new column) is true only while the current assignment was obtained by self-service claiming out of the open escalation pool — that admin must resolve it directly, they can't escalate again. A reassigned admin (even one reassigned out of the escalation pool, or one who receives a case that was escalated earlier in its history) has this reset to `false` and *can* escalate again — reassignment is a deliberate hand-off, not the receiving admin opting into being the end of the line. `escalatedByAdminId` itself is no longer the escalate-again gate (it's a permanent historical marker, overwritten to whoever escalates each time, used only for that escalator's own claim-lockout).
- **Stale-unclaimed notification (24h)**, independent of the existing 7-day auto-escalation: a case still `OPEN` past `COMPLIANCE_CASE_STALE_NOTIFY_HOURS` (24) gets an in-app `AdminNotification` sent to admins holding the new `VENDORS_COMPLIANCE_RECEIVE_STALE_ALERT` permission who are **country-scoped** to the vendor's own country (global admins deliberately excluded — same reasoning as the sidebar compliance dot). Fires once per case (`staleNotifiedAt`). Wired into `compliance-case-sync.job.ts` alongside the existing auto-resolve/auto-escalate reconciliation.
- **Document remediation review.** A vendor-account document (not an application-time one) tied to a currently active compliance case can only be approved/sent-back-for-revision by that case's claimed owner (`approveDocument`/`rejectDocument` in `admin.vendor.service.ts` gained this gate). Framed to admins as "send back for revision," not "reject" — mechanically the same `REJECTED` + `revisionNotes` shape that already exists for application-time documents, just different framing for this context; no new `DocumentStatus` value was added. Escalating a stuck remediation happens via the existing `/vendors/compliance` Escalate action, not a duplicate control inside the document view.
  **Known gap, not silently built around**: there is currently no vendor-facing way to actually upload a document against an active `VendorAccount` at all (`upsertVendorDocument`/`presignDocumentUpload` in `vendor.document.service.ts` both hard-require an editable `VendorApplication` — confirmed by reading them). The admin-side review capability above is correctly wired and ownership-gated, but nothing will exercise it until that vendor-facing upload path is built — which requires touching `apps/vendor-dashboard` + the vendor module backend, both explicitly out of scope until now. This is the concrete, first-found reason the next phase (below) needs to open that boundary.

**New admin-facing notification center** (`AdminNotification` model, the `AdminUser` counterpart to vendor-facing `VendorNotification`) — in-app only, no email/push. `admin.notification.service.ts` (list/unread-count/mark-read/mark-all-read, every admin sees only their own rows), routes at `/admin/v1/notifications/*` (no permission gate — any authenticated admin manages their own notifications). Frontend: a real `/notifications` page (replacing the placeholder stub) and a `NotificationBell` navbar component polling `/api/notifications/unread-count` every 60s — same "subtle glow, not live counter" convention as the sidebar compliance dot.

**After this roadmap**: outlet administration (no `admin.outlet.*` surface exists at all today) is the recommended next initiative, and the one expected to require touching `apps/vendor-dashboard` for the first time. Confirm scope with a fresh recon when this roadmap's P0+P1 (and any P2 you want) are done — don't assume the earlier outlet notes below are still complete by then.

## Backend admin module (`apps/backend/src/modules/admin`)

Pattern: `routes/v1/*.routes.ts` → `controllers/*.controller.ts` → `services/*.service.ts`. Middleware chain on every admin route: `verifyAdminToken → loadAdminUser → checkIsActive → loadPermissions → buildScopeContext`, then per-router gates (`requirePermission(X)`, and for Identity & Access, `requireIdentityAccess` restricting to `super_admin`/`identity_admin` only).

**RBAC**: pool-based. `AdminRolePermission` = a role's permission ceiling; `AdminUserPermission` = individual grants (must be within the role's pool). Roles: `super_admin` (all permissions), `identity_admin`, `finance`, `vendor_ops`, `customer_care`, `courier_ops`. Seed data lives in `packages/database/src/seed/admin/data/` (`roles.data.ts`, `permissions.data.ts`, `role-permissions.data.ts`) — idempotent upserts, safe to re-run via `pnpm db:seed`.

**Geographic scope** (`AdminUserScope`): `AdminScopeType` is `GLOBAL` / `COUNTRY` / `CITY` only — this is the full enum, in both `schema.prisma` and `packages/types/src/enums/admin.ts`. **`REGION` is not a valid admin scope anywhere in the codebase today** — it does not exist as an enum value, `AdminUserScope` has no `regionId`, and `buildScopeContext`/`AdminScopeContext` (`isGlobal`, `countryIds`, `cityIds`) has no region concept. The `Region` model is a separate, unrelated thing: a geography grouping entity (`Country.regionId`) managed by `admin.region.service.ts` for reporting/organization, gated on `scope.isGlobal` like any other global-only config — it is not wired into the authorization system at all. Adding regional admin scope would need a schema migration (new enum value, `AdminUserScope.regionId`) plus changes to `buildScopeContext` and every service's scope-filter logic, not just a "preserve what's there" effort.

Role vs. scope: **role determines permissions, scope determines where they apply, and roles differ in which scopes they're allowed** — enforced by `ROLE_SCOPE_RULES` in `apps/backend/src/modules/admin/lib/scope/scope-rules.ts`. Today: `super_admin` → `GLOBAL` only, pool = every permission in `ALL_PERMISSION_KEYS` (`role-permissions.data.ts`) — a seed-time default, not a hard constraint, so a restricted-but-still-global superadmin variant is possible without an architecture change. `identity_admin` → `GLOBAL` or `COUNTRY`. `finance` → `COUNTRY` only. `vendor_ops` → `COUNTRY` or `CITY` only (**not `GLOBAL`, and `REGION` doesn't exist** — so "global vendor ops" isn't currently possible without both a scope-rule change and a permission-pool decision). `customer_care`/`courier_ops` → `CITY` only. `operations_admin` → `GLOBAL` only (its own seed description says "global scope only for now" — no country or regional variant exists yet). Extending any role to more scope types is a one-line change to `ROLE_SCOPE_RULES` (plus a pool decision) — the mechanism already generalizes; only the specific role→scope mappings above are narrow today.

**Audit logging**: every mutation calls `auditService.log({ adminUserId, action, entityType, entityId, changes, metadata })`, writing to the append-only `AuditLog` table (archived after 90 days, deleted after 730). Action strings follow `entity.verb` (e.g. `country.activated`, `vendor_type_country.assigned`).

## Vendor management (`apps/backend/src/modules/vendor` + `admin.vendor.*`)

A vendor is **country-scoped**: `VendorAccount.countryId` is set at approval and never changes; `companyRegNumber`/`taxRegistrationNumber`/`businessPhone` are unique per-country, not globally. The same real-world business operating in two countries needs two separate applications/accounts — there is no cross-country vendor entity.

**Lifecycle**: `VendorApplication.status` (`DRAFT → SUBMITTED → UNDER_REVIEW → NEEDS_REVISION ↺ → APPROVED/REJECTED`) is vendor-editable only in `DRAFT`/`NEEDS_REVISION`. Approval is transactional: creates the `VendorAccount` (`ACTIVE`/`SUSPENDED`), copies over approved/pending documents, and requires every required `VendorDocument` to already be `APPROVED` (`assertAllRequiredDocumentsApproved`). `VendorLifecycleState` (`packages/types/src/domain/vendor.ts`) is the single derived field (never stored) the frontend should switch UI on.

**Review workflow** is a full claim/reassign/escalate system, not a bare approve/reject: `assignedReviewerId` = current owner (unclaimed = anyone with `VENDORS_APPLICATIONS_REVIEW` may act); `assertReviewerOwnership` enforces only the assignee (or a `VENDORS_APPLICATIONS_REASSIGN` holder) can act once claimed; escalation permanently locks the escalating admin out of that application and drops it into an "open pool" claimable only by `VENDORS_APPLICATIONS_RECEIVE_ESCALATION` holders. Reject/needs-revision require a `reasonCode` resolved via `AdminActionReason` (country-specific override falls back to a global code).

**Vendor identity is single-user today**: `VendorUser` is 1:1 with both `VendorApplication` and `VendorAccount` — no owner/manager/staff multi-user model exists. The `StaffRole` enum (`OWNER`/`ADMIN`/`MANAGER`/`CHEF`/`STAFF`) is defined in `schema.prisma` but is entirely unwired (no relation uses it) — treat it as a future placeholder, not working code. Banning is **identity-level** (`VendorUser.isBanned`, via `banVendor`/`unbanVendor`) and independent of `VendorAccount.status` (`suspendVendor`/`reinstateVendor`); a banned vendor's UI badge takes precedence over the account status. Both suspend and ban deactivate/soft-delete payout accounts (vendor must re-add and re-verify after either).

**Documents**: one `VendorDocument` model serves both phases (`applicationId` while applying, transferred to `vendorId` on approval). Requirements come from `DocumentTypeConfig` (country + optional city scope) joined to vendor types via `DocumentTypeVendorType` (no link rows = required for every vendor type in that country by default). Outlet-level and city-scoped ("upload once, inherit to all outlets in that city") documents are separate (`OutletDocument`, `OutletDocumentInheritance`).

**Outlets** are a vendor's city-scoped operating locations (`Outlet.cityId`, `vendorId`). Vendor-side self-service create/update runs automatic flag checks (profanity, duplicate name in city, duplicate coordinates within `OUTLET_PROXIMITY_DEGREES`) that set `reviewStatus: FLAGGED`. **Admin-side moderation — done (2026-08-27), see "Admin-side outlet moderation" below.** The vendor account detail page still only lists outlets read-only (a `VendorOutletsMap` read-only Mapbox multi-marker view, see "Vendor Accounts/Applications enterprise pass" below — display only, deliberately not linked into the new moderation page this pass, findable there via its own search instead). Note for future outlet work: `Outlet.cityId` is a **plain scalar FK, not a Prisma relation** — `City` has no `outlets Outlet[]` back-relation and `Outlet` has no `city City @relation(...)` field, so a city name can't come through a Prisma `include`; both `getVendorAccount` and the new `admin.outlet.service.ts` batch-fetch city names for their outlets as a second query instead.

**Admin-side outlet moderation — done (2026-08-27).** Closes the gap this file documented since the original vendor-management recon. New `admin.outlet.service.ts`/`admin.outlet.controller.ts`, routes mounted on the existing `vendorRouter` at `/admin/v1/vendors/outlets/*` (same file as appeals/profiles, not a separate top-level router — outlets are conceptually vendor-nested). Two independent axes, matching what the schema already implied:
- **Review** (`reviewStatus`) resolves a vendor-side flag — approve (clears it, doesn't itself change `adminStatus`) or reject-with-required-reason (also just a verdict, deliberately does **not** auto-suspend — same "the flag is visible, the operational action stays separate" pattern used for compliance issues never auto-suspending a vendor). `Outlet` gained a `rejectionReason` column (migration `20260827120000_add_outlet_moderation_reasons`) mirroring `VendorProfile.rejectionReason` — cleared on the vendor's next edit that recomputes flags, same convention.

New permissions `VENDORS_OUTLETS_READ`/`VENDORS_OUTLETS_MODERATE` (`vendor_ops` pool only, plus `super_admin`). New page `/vendors/outlets` — stat cards (Flagged/Suspended/Banned), review-status tabs (defaulting to Flagged) plus an admin-status filter, country/search filters, per-row `OutletModerationActions` (approve/reject when flagged; suspend/ban when active; reinstate/ban when suspended; unban when banned) — same `TableFilterBar`/tabs shell as `/vendors/appeals` and `/vendors/profiles`. Sidebar "Vendors" section today: Home, Applications, Accounts, Revenue (`apps/admin-dashboard/utils/constants/nav-items.ts`) — no Outlets entry, matching the backend gap above. Vendor Categories (formerly "Vendor Types") is its own top-level sidebar section, not nested here — see below.

**Compliance framework phase 2/3 (2026-08-25)** — implements the framework recommended at the end of the prior pass. Schema migration `20260825120000_add_compliance_severity_grace_waivers`:
- `DocumentTypeConfig` gained `complianceSeverity` (`LOW`/`MEDIUM`/`CRITICAL`, default `MEDIUM`), `gracePeriodDays` (default `0`), `enforcedFrom` (nullable) — all additive with defaults that preserve prior behavior for every existing row. These live on `DocumentTypeConfig`, not `VendorDocument` — deliberately, since `DocumentTypeConfig` already covers `VENDOR`/`OUTLET`/`CITY` scope uniformly (see `DocumentScope`), so the same severity/grace/rollout mechanism already applies to outlet and city-scoped document types too, no schema change needed when outlet compliance is built later. This is the "set the stage for outlets" groundwork from that conversation — deliberately just the schema shape, not outlet compliance itself (still fully deferred, see below).
- New `VendorComplianceWaiver` model — an admin-granted exception on one vendor+documentType issue (`reason`, `expiresAt`, `grantedByAdminId`, revocation fields). **Vendor-scoped only, on purpose**: when outlet administration is eventually built, the expected shape is an analogous `OutletComplianceWaiver`, not a migration of this model into something polymorphic — Prisma polymorphic relations are painful, and there's no outlet compliance to exercise a generalized version against yet.
- New permission `VENDORS_ACCOUNTS_COMPLIANCE_MANAGE` (`vendors:accounts:compliance_manage`) — gates waive/revoke-waiver, granted to `vendor_ops` (alongside its existing `suspend`/`ban`) and `super_admin` (via `ALL_PERMISSION_KEYS`); `operations_admin` does not hold it (matches its country-launch-config focus, not vendor-account actions).

**`getComplianceOverview` rewrite** (`admin.vendor.compliance.service.ts`) — now computes three issue kinds, not two:
- **MISSING** (new) — a vendor lacks an `APPROVED` document for something currently required. Computed as a vendor × required-document-type diff, reusing the vendor module's own `getAllowedDocumentTypes` (`vendor.document.service.ts`) — the exact same "no `DocumentTypeVendorType` rows = required for every vendor type in the country" rule the live onboarding flow already enforces, not a re-derived copy of it. Respects `enforcedFrom`: a requirement whose `enforcedFrom` is still in the future doesn't yet count as MISSING for already-approved vendors — see the framework note below for why. Computed in application code over a bounded scan (`MAX_COMPLIANCE_VENDOR_SCAN`/`MAX_COMPLIANCE_DOCUMENT_SCAN` in `constants/vendor.ts`, 1500/3000) since there's no row to paginate over in SQL for something that doesn't exist — documented as an admin-tool-scale ceiling, not a claim of unlimited scale; a materialized/scheduled snapshot is the natural next step if a deployment outgrows it.
- **EXPIRED** / **EXPIRING_SOON** — same as before, but now classified with each document type's own `expiryWarningDays`/`gracePeriodDays` (mirrors `computeVendorCompliance`'s precision) instead of a flat lookahead window. An `EXPIRED` row now carries `inGracePeriod: boolean` — past expiry but still within the grace window — shown as a softer "Expired (grace period)" badge rather than a separate top-level status/tab.
- **WAIVED** — an overlay, not a fourth independently-detected kind: any MISSING/EXPIRED/EXPIRING_SOON candidate with an active (non-revoked, unexpired) `VendorComplianceWaiver` gets its status flipped to `WAIVED` and is excluded from the urgent counts (`missingCount`/`expiredCount`/`expiringCount`/`affectedVendorCount`) — but stays visible under the Waived tab rather than disappearing, since a waiver is meant to be auditable, not a way to make an issue vanish.
- Response field renamed `documents` → `issues` (it's no longer purely `VendorDocument`-backed) and `vendor` is now always present (never `null`) since both detection paths only ever produce rows for a resolved `VendorAccount`.
- `getExpiringDocuments`/`getExpiredDocuments` (the original two-endpoint phase-1 functions) are untouched and still routed — `getComplianceOverview` was already a separate computation from them, not a wrapper, so this pass extending it didn't touch them either.

**`/vendors/compliance` UI**: five tabs (All / Missing / Expired / Expiring Soon / Waived), six stat cards, a Waive/Revoke action per row (`ComplianceIssueActions.tsx`, an `AlertDialog` — reason + expiry date to waive, optional reason to revoke) gated on `VENDORS_ACCOUNTS_COMPLIANCE_MANAGE`. Deliberately does **not** duplicate the suspend/ban flow here — that stays exclusively on the vendor detail page (`VendorAccountActions.tsx`); "View →" is one click away. Waiving is the action that's actually specific to a compliance issue, so it's the only one that got a new per-row control.

**Vendor module backend — analyzed, left unchanged, findings documented rather than silently doing nothing**: `getAllowedDocumentTypes` (the resolver a *new* vendor application uses to know what documents to ask for) deliberately does **not** get an `enforcedFrom` check — `enforcedFrom` is a transition/grace concept for *already-approved* vendors catching up to a new requirement; a brand-new applicant should always be held to whatever is required today, full stop. Also confirmed there is no `admin.outlet.*` or `vendor.profile.*` backend service — `VendorProfile` (public profile) and `Outlet`/`OutletDocument` are schema-only or vendor-onboarding-only today; see the recommendation on vendor lifecycle sequencing for what that implies.

**Compliance framework phase 2/3 continued — case workflow, notifications, sidebar dot (2026-08-25)**: the bug this pass started from — the vendor detail page's Compliance section always said "no compliance issues" — was because it computed compliance from `account.documents` alone (`computeVendorCompliance`), which by definition cannot see a document that was never uploaded (MISSING). Fixed by extracting `detectComplianceCandidates` as the one shared detection core (MISSING + EXPIRED + EXPIRING_SOON + waiver overlay) that both `getComplianceOverview` (cross-vendor) and the new `getVendorComplianceIssues` (one vendor) call — `computeVendorCompliance`/`getVendorComplianceSummary` are deleted, not deprecated. `getVendorAccount`'s `compliance` field is now `null` unless the caller holds `VENDORS_COMPLIANCE_READ` (a new, dedicated permission — viewing compliance is gated separately from `VENDORS_ACCOUNTS_READ` now, on the overview page and this nested field alike).

**Claim/escalate case workflow** (`admin.vendor.compliance-case.service.ts`, new file) — modeled as closely as possible on `VendorApplication`'s review workflow (same `assignedReviewerId`/`escalatedByAdminId`/permanent-escalator-lockout shape), backed by the new `VendorComplianceCase` model. One deliberate deviation from the applications pattern: claiming a case out of the escalation pool requires the claimant be **country-scoped** to the vendor's own country — a globally-scoped holder of `VENDORS_COMPLIANCE_RECEIVE_ESCALATION` still can't claim it (`claimComplianceCase`). Compliance follow-up stays with the local country team by design; the applications escalation pool has no such restriction. `claimComplianceCase`/`escalateComplianceCase` can open a case on the fly (get-or-create) — they don't depend on the reconciliation job having already created one for a fresh issue. New permissions: `VENDORS_COMPLIANCE_READ`, `VENDORS_COMPLIANCE_CLAIM`, `VENDORS_COMPLIANCE_ESCALATE` (all in `vendor_ops`'s pool; `RECEIVE_ESCALATION` is ceiling-only, granted individually to specific senior reviewers, same pattern as `VENDORS_APPLICATIONS_RECEIVE_ESCALATION`). Reassign was deliberately **not** built — cheap to add later, but a half-wired permission with no UI wasn't worth shipping this pass.

**Reconciliation cron** (`jobs/vendor/compliance-case-sync.job.ts`) keeps `VendorComplianceCase` rows in sync with live detection — opens a case for any live candidate that doesn't have one yet, moves a case to `WAIVED` if its issue gets waived, auto-`RESOLVED`s a case whose issue no longer appears at all (the vendor fixed it). Runs on the same cadence as the document-expiry cron (offset 15 minutes so they don't contend), looped per-active-country to stay within `detectComplianceCandidates`' scan caps. This is also what makes the sidebar dot cheap: `hasOpenComplianceIssuesForCountries` reads `VendorComplianceCase` (one indexed query), it does not re-run detection.

**Sidebar "Compliance" nav dot**: a small glowing red dot, shown only to a **country-scoped** admin holding `VENDORS_COMPLIANCE_READ` with at least one open case in their own country — never shown to global admins (who always have issues somewhere, so the nudge wouldn't mean anything the way it does for a country team watching their own patch). Wired through `AdminSessionData.hasOpenComplianceIssues`, computed in `admin.session.controller.ts` (the one intentional exception to `buildAdminSession` staying a pure zero-DB-call transform — kept out of that function on purpose, done as an extra awaited call in the controller instead). Piggybacks on the session endpoint's existing 5-minute frontend cache, so "subtle glow," not a live counter, is the actual behavior, not just the intent.

**Notify** (`notifyVendorAboutComplianceIssue`) — repeatable, unlike suspend: writes a `VendorNotification` row (new model, vendor-facing, **backend-only this pass** — no vendor-dashboard UI reads it yet, deliberately, since vendor-dashboard stays untouched until outlet work begins) and best-effort emails the vendor via a new `lib/email/mailer.ts` (`nodemailer`, SMTP-configured via env, **no-ops with a logged warning if `SMTP_HOST` is unset** — same "works without the real thing configured" convention as mock revenue data) using a branded HTML template (`lib/email/templates/compliance-notice.ts`, severity-colored accent, support-email footer, CTA to `VENDOR_DASHBOARD_URL` if set). A failed or skipped send never blocks the `VendorNotification` row or the audit log entry — email is best-effort on top of the durable record, not the record itself.

**Severity is admin-configurable, not fixed** — `complianceSeverity`/`gracePeriodDays`/`enforcedFrom` are now real fields on both document-type forms (`DocumentTypeFormSheet.tsx` create, `DocumentTypeFormDialog.tsx` create+edit), not just schema defaults. The compliance page uses severity to sort (most severe first, within each status) and to gate one UI affordance: a "Suspend vendor" shortcut link only appears on a `CRITICAL`-severity issue — it links to the vendor detail page rather than duplicating the suspend flow inline, so suspend stays the one place that action lives.

**Set the stage for outlets — what actually changed vs. what didn't**: `complianceSeverity`/`gracePeriodDays`/`enforcedFrom` live on `DocumentTypeConfig`, which already spans `VENDOR`/`OUTLET`/`CITY` scope — so outlet-document compliance will reuse these fields with zero migration once outlet administration exists. `VendorComplianceCase`/`VendorComplianceWaiver`/`VendorNotification` are all vendor-scoped by name and by FK on purpose — no speculative nullable `outletId` columns were added ahead of there being any outlet data to reference. When outlet work starts, the expected shape is analogous outlet-scoped siblings (`OutletComplianceCase`, etc.), not a retrofit of these into something polymorphic.

**Filter-bar responsiveness pass (2026-08-25)**: `TableFilterBar` — used by `/vendors/applications`, `/vendors/accounts`, and now `/vendors/compliance` — previously had no `flex-wrap` on its row layout (`lg:flex-row`) and a `flex-1`-growing search input; with five-plus fields active (search, status, country, category/doc-type, sort, dir, buttons) this could overflow the card at intermediate widths instead of wrapping. ## Frontend admin-dashboard conventions

- Server components fetch via `adminFetch()` (`lib/api`), tagged for `revalidate`/`router.refresh()` invalidation.
- Mutations go through Next route handlers under `app/api/**` that proxy to the backend (never call the backend directly from client components).
- Shared UI: `TableFilterBar` (search/status/country/sort/date-range — extend it rather than building bespoke filter bars), `TablePagination`, `EmptyState`, `admin-card`/`icon-badge`/`badge-*` utility classes, `AlertDialog`-based confirm/action dialogs (see `CountryActions.tsx`, `VendorCategoryCountryBreakdown.tsx` for the canonical pattern), `Sheet` for actual create/edit forms (see `VendorCategoryFormSheet.tsx`) — AlertDialog is for short confirmations, Sheet is for forms, don't mix the two up.

When adding a new sibling nav item under an existing "Home", check whether that section's href already needs (or now needs) this treatment.

## Operational geography + vendor-onboarding surface (2026-08-29 → 2026-08-30)

A user-directed series building the geography → outlet → go-live spine, in a fixed 7-item order, **with an explicit rule: no external paid APIs** (no payment gateways, no telco name-lookup, no Plaid, no ML/vision moderation, no doc-OCR). Every place one of those *would* go is behind an in-house interface with a working no-API implementation, so wiring a real provider later is one file. Migrations: `20260829120000_add_operational_zones`, `20260829140000_add_zone_change_notifications`, `20260829160000_add_market_signals`, `20260829222804_add_outlet_clearance_status`, `20260829231117_add_outlet_document_notification_types`, `20260830014630_add_outlet_compliance`, `20260830022412_add_outlet_inspections`, `20260830025624_add_profile_flag_details`, `20260830140807_add_payout_hardening`.

**The axis-decomposition principle** (runs through everything here): an entity's *capability* (may it operate at all), *operational health* (is it currently up), and *content/moderation state* are three separate fields, never collapsed. `Zone.level` / `Zone.operationalStatus` / `Zone.status`. `Outlet.clearanceStatus` / `Outlet.adminStatus` / `Outlet.reviewStatus`. Go-live answers (`getVendorGoLiveStatus`, `getOutletGoLiveStatus`, `getOutletMealPlanReadiness`) are **computed live, never stored** — the backend is authoritative and both dashboards render off the resolver, never re-deriving.

### Operational zones + market signals (`Zone`, `MarketSignal`, `@repo/geo`)

**`Zone`** — a capability container *inside* a city (`Zone.cityId`, GeoJSON `boundaries`). Two orthogonal axes plus record lifecycle:
- **`level`** (`ZoneLevel`: `REGISTRATION_ONLY` → `MARKETPLACE` → `PLATFORM_DELIVERY` → `FULL_OPERATIONS`) — monotonic capability ladder. Promotion/demotion is an explicit audited admin decision (`SETTINGS_ZONES_SET_LEVEL`), never automatic. **`ZONE_CAPABILITIES` (`packages/geo/src/capabilities.ts`) is the ONE place a level maps to boolean flags** (`canListOnDemand`, `canOfferMealPlans`, …) — business logic checks the flag, never `level >= X`. `canOfferMealPlans` is true only at `FULL_OPERATIONS`.
- **`operationalStatus`** (`ZoneOperationalStatus`: `ACTIVE` / `SUSPENDED` / `MAINTENANCE` / `EMERGENCY`) + `pausedUntil` — "is this zone up right now," independent of level.
- **`status`** (`GeoStatus`) — the record's own active/retired lifecycle, mirrors `ServiceArea`/`DeliveryZone`/`City`.

`@repo/geo` gained pure (no-I/O, no `@repo/db`) modules: `capabilities.ts`, `polygon.ts`, `distance.ts`, `point-in-polygon.ts`. `resolveCapabilities()` takes a point (or an outlet's known zone) + the city boundary + zones and returns the full `ResolvedZoneCapabilities` picture. `vendor.geography.service.ts` is the DB-aware wrapper — `resolveCapabilitiesForOutlet`, `resolveCapabilitiesForPoint`, `recomputeOutletZonesForCity` (re-runs point-in-polygon for every outlet in a city when zone geometry changes).

**Zones are CITY-granular scope** — the one geography resource that is (the rest of the admin module is country-granular). A `CITY`-scoped admin (city launch team) touches only their own city's zones; a `COUNTRY`-scoped admin, any city in their country. New permissions `SETTINGS_ZONES_READ` / `_WRITE` / `_SET_LEVEL` / `_RECEIVE_ALERT` — deliberately **separate from `settings:geography:*`** (the city *boundary* is a global concern; drawing/tuning zones inside a launched city is local ops work). `_SET_LEVEL` is a ceiling entry (grant individually). Backend: `admin.zone.service.ts` / `admin.zone.controller.ts` / `admin.zone.routes.ts` (`/admin/v1/zones`, `/admin/v1/cities/:cityRef/zones`), boundary validated within the city boundary + approximate overlap check against sibling zones. `admin.zone.notification.service.ts` fires `ZONE_STATUS_CHANGED` / `ZONE_CAPABILITY_CHANGED` (in-app `AdminNotification` + email for country/city-scoped `SETTINGS_ZONES_RECEIVE_ALERT` holders) on suspend/retire/reactivate/level-change. Frontend: `/cities/[citySlug]/geography` (`CityGeographyWorkspace`, `ZoneEditPanel`, `zone-meta.ts`).

**`MarketSignal`** (`MarketSignalType`: `VENDOR_INTEREST` / `CUSTOMER_INTEREST`) — supply/demand captured *ahead* of operating somewhere, the two independent launch inputs that **inform, never auto-trigger** an admin's decision to create a zone or promote a level. Captured at a lat/lng, tagged with its zone if inside one, else bucketed as unzoned-in-boundary / outside-boundary. CITY-granular scope, same rule as zones. `admin.marketSignal.service.ts`, routes `/admin/v1/market-signals` + `/admin/v1/cities/:cityRef/market-signals`. Frontend: `CityLaunchSignalsPanel` on the same geography page. `CUSTOMER_INTEREST` carries contact fields only for now (no `ConsumerAccount` to point at yet).

### #1 — Outlet lifecycle decomposition + `getOutletGoLiveStatus`

### #4 — Outlet compliance framework

`jobs/vendor/outlet-compliance.job.ts` (registered in `bootstrap/externalServices.ts`, runs right after `document-expiry`, per active country, bounded by `MAX_OUTLET_COMPLIANCE_SCAN`):
1. **Escalating pre-expiry reminders** — for each current outlet document with an expiry date, notify the vendor as it crosses each `OUTLET_DOC_EXPIRY_REMINDER_THRESHOLDS` day-mark (`60/30/14/7/3/1/0`), deduped via `OutletDocument.lastExpiryReminderDaysOut` so each threshold fires once. Descending intervals, not a daily blast — matches how Uber Eats / DoorDash escalate merchant-document reminders.
2. **Auto-suspend** — a `CRITICAL` required outlet document expired **past its `DocumentTypeConfig.gracePeriodDays` window** takes the outlet offline (`adminStatus: SUSPENDED_COMPLIANCE`, clearance `PENDING_DOCUMENTS`), vendor + scoped admins notified (`OUTLET_SUSPENDED_COMPLIANCE`, `OUTLET_AUTO_SUSPENDED`). Comes back **automatically** when the renewed document is approved (`OUTLET_COMPLIANCE_RESOLVED`). Non-`CRITICAL` expired documents are surfaced, never auto-acted — a human decides, same as the vendor-account compliance framework.

`admin.outlet.notification.service.ts` — `notifyVendorOutletCompliance`, `notifyAdminsOutletAutoSuspended`. Email templates `outlet-compliance-notice.ts`.

### #5 — Outlet inspections + meal-plan readiness

**`OutletInspection`** model + `OutletInspectionPolicy` on `Country` (`NONE` / `MEAL_PLAN_ONLY` (default) / `ALL`) — default mirrors Uber Eats / DoorDash: an on-demand marketplace listing never requires a physical visit, meal-plan (subscription-kitchen) eligibility does. `OutletInspectionStatus`: `SCHEDULED` / `IN_PROGRESS` / `PASSED` / `FAILED` / `WAIVED` / `CANCELLED`.

`admin.outletInspection.service.ts` — deliberately **far simpler than the compliance-case machinery**: no claim / escalate / reassign. ### #7 — Payout hardening (no API)

## Finance module — provider-agnostic, country-isolated financial foundation (`apps/backend/src/modules/finance`)

DailyBread Global sits above independent per-country financial environments. A vendor belongs to one country and can never use another country's financial rails. Payment providers (Flutterwave, dLocal, and later Stripe/Adyen/…) are **replaceable adapters** behind a capability abstraction — no part of the domain ever sees a provider SDK, URL, payload, header, status string or error, only normalized types.

**Schema (Prisma, migrations `20260831…` → `20260907000000_finance_capability_routing`):**
- `Currency` (ISO-4217 reference, `minorUnitDigits` — never assume 2) · `Country.currencyCode` FK (mid-migration alongside the legacy `Country.currency` string).
- `PaymentProvider` — the catalog of provider *implementations* the system can talk to (`code`, declared `capabilities: PaymentProviderCapability[]`, `methodTypes`, `supportedCurrencies`). Not credentials, not per-country wiring.
- `CountryProviderAccount` — "this country uses THIS provider account, in THIS `environment` (TEST|LIVE)". Append-only (retire via `status = DISABLED`, never deleted). `secretAlias` is a non-secret pointer; real credentials live outside the DB (`ProviderSecretsResolver`, env-backed, secret-manager-swappable). `@@unique([id, countryId])` powers the composite same-country FKs below. **A country may have MANY `ACTIVE` accounts at once — one per capability domain.** There is no "the country's active/primary account" and no such column.
- `CountryFinancialConfig` (1:1 with Country) — currency mirror + operational switches (`collectionsEnabled`/`payoutsEnabled`) + `status` lifecycle (DRAFT/ACTIVE/SUSPENDED/DISABLED) + **exactly one explicit routing binding: `bankVerificationProviderAccountId`** (composite FK `(id, countryId) → (id, countryId)` — DB-enforced same-country), for the country-global `BANK_ACCOUNT_RESOLUTION` capability (`BANK_LIST` routes with the payout method instead — see below).
- `CountryPaymentMethod.countryProviderAccountId` — composite same-country FK; the routing source for method-specific capabilities.
- `ProviderWebhookEvent` — provider-event idempotency boundary (`@@unique([provider, providerEventId])`); the Flutterwave inbound handler verifies a signature against every non-DISABLED Flutterwave account (multi-account-safe, doesn't use `resolveProviderGateway`).

**Capability-scoped provider routing — `finance.providerGateway.service.ts` (`resolveProviderGateway`):**
`business op → required capability → route class → country → specific CountryProviderAccount → adapter → provider`. `providerRouteClassFor(capability)` (`provider.capabilities.ts`, pure, unit-tested) is the ONE place capability → route class is decided:
- **`PAYMENT_METHOD`** (`COLLECTION_*`, `PAYOUT_*`, `REFUND`, `BANK_LIST`) → resolved via a specific `CountryPaymentMethod.countryProviderAccountId`. The caller **must** pass `opts.countryPaymentMethodId`; without it → `ROUTING_CONTEXT_REQUIRED`. Never guessed.
- **`BANK_VERIFICATION`** (`BANK_ACCOUNT_RESOLUTION` only) → resolved via `CountryFinancialConfig.bankVerificationProviderAccountId`. Independent binding — **never inferred from a collection/payout provider account**.
- **`UNROUTABLE`** (`WEBHOOKS`) → not resolvable through the gateway.
There is **NO fallback of any kind** — no "active/primary/first-ACTIVE provider", no provider guessing. A missing or unusable route is an explicit config error (`PROVIDER_ACCOUNT_NOT_CONFIGURED` / `PROVIDER_ACCOUNT_NOT_ACTIVE` / `PROVIDER_CAPABILITY_NOT_ENABLED` / …). Cross-country routing is structurally impossible (both routing links are composite same-country FKs; the gateway also asserts `account.countryId === countryId`).

**Financial readiness — `finance.readiness.{service,compute}.ts` (the ONE readiness system):** pure decision core, capability-scoped. Per dimension it checks that a *usable* provider account (ACTIVE · provider ACTIVE · env matches deployment · adapter registered · credentials resolvable · enables the needed capability) is actually wired — collection/payout each resolve their own payment method's wired account; bank verification resolves the config binding; a BANK payout method additionally depends on the bank-verification route. Consumed by `admin.country.service.ts` (country-activation / vendor-onboarding / customer-ops gates) and the ERP config view. `FinancialReadiness` output shape is unchanged.

**Provider account lifecycle (`finance.providerAccount.service.ts`):** `activate` has NO "one ACTIVE per country" check (removed — routing is explicit). `disable` nulls every pointer at the account (the bank-verification binding + every `CountryPaymentMethod` wiring) so nothing silently keeps routing to a dead account; append-only otherwise. Structural/lifecycle mutations require GLOBAL finance scope; DRAFT editing allowed for a country-scoped finance admin on their own country; city-scoped refused. Opaque-id endpoints 404 (not 403) outside scope.

**Vendor payout verification — behaviourally unchanged, only its provider lookup moved.** `vendor.payout.service.ts` → `getPayoutVerificationProvider()` → `lib/payout-verification/finance-bank.provider.ts` → `resolveProviderGateway(countryId, "BANK_ACCOUNT_RESOLUTION")` (and `"BANK_LIST"` for the bank picker), both now routed via the config's `bankVerificationProviderAccountId`. Structural checksums still gate a malformed identifier with a 400 before any row; provider outcomes still map to `VERIFIED` / `FAILED` / `REQUIRES_REVIEW` / `PENDING` exactly as before; any `resolveProviderGateway` config error still degrades gracefully to the offline structural-check + manual-review path. Risk logic, masking/encryption/blind indexes, `getVendorGoLiveStatus` (only `VERIFIED` satisfies selling readiness), admin manual-verify guard (a definitive provider rejection can't be flipped to VERIFIED) — all untouched. The vendor payout account stays owned by the Vendor domain; Finance owns provider capability/routing/adapter infrastructure only.

**Provider adapters (`finance/providers/`):** each is a stateless, capability-segregated implementation behind `provider.types.ts` contracts; registered once at boot in `register-adapters.ts`; the finance domain only ever gets one from the registry and calls a normalized capability on it.
- **Flutterwave** (`providers/flutterwave/`) — OAuth2 v4. Implements collection / refund / bank payout / bank-account resolution (NGN only) / bank list / webhooks.
- **dLocal** (`providers/dlocal/`) — the **first provider for `BANK_ACCOUNT_RESOLUTION`**. Implements **that capability only** (`bankResolution`); its collection/payout rails are separate APIs and separate future phases, so the catalog row + adapter declare nothing else — capability support stays honest. Endpoint: `POST {base}/payouts/validation/external-account` (classic API v2.1). Base: `sandbox.dlocal.com` (TEST) / `api.dlocal.com` (LIVE), per the account's `environment`, per-account `baseUrl` override. Auth = **HMAC, not OAuth**: headers `X-Login` / `X-Trans-Key` / `X-Date` / `X-Version: 2.1` + `Authorization: V2-HMAC-SHA256, Signature: <hmac_sha256_hex(secretKey, X-Login + X-Date + body)>` (`dlocal.signature.ts`, pure + unit-tested against a node-crypto reference). Credentials (`xLogin` / `xTransKey` / `secretKey`) are self-service from the dLocal Merchant Dashboard, separate Test/Live; resolved via the existing `secretAlias` mechanism (`FINANCE_PROVIDER_SECRET__DLOCAL_<CC>_<ENV>__{XLOGIN,XTRANSKEY,SECRETKEY}`), `requiredSecretKeys` declared so the no-network completeness check works. dLocal's account-validation is **country-keyed and country-limited** (dLocal documents ~10 countries): `DLOCAL_ACCOUNT_VALIDATION` (`dlocal.accountValidation.ts`) is the single source of truth for which countries the adapter supports + how to build each one's request — **Nigeria (NG)** is the only entry today (`country` + `account_type: BANK` + `bank_code` + `account`; NIBSS 3-digit codes, which dLocal accepts); an unsupported country fails fast with `UNSUPPORTED_CAPABILITY` **before any network call** (same pattern as Flutterwave's currency guard) → the caller degrades to manual review, never a false FAILED. `ResolveBankAccountInput` gained `countryCode` (ISO-3166 alpha-2, provider-agnostic — the vendor's own country) which the Finance gateway fills from the routed provider account's country (`ResolvedProviderGateway.account.countryCode`); Flutterwave ignores it. Response: dLocal `status`/`status_code` `1000` = success (→ `full_name` → `accountName`); codes 1011–1017 → `TRANSACTION_DECLINED` (FAILED); 1006 → `UNSUPPORTED_CAPABILITY`; 1007 → `PROVIDER_UNAVAILABLE`; HTTP 401/403 → `AUTHENTICATION`, 429 → `RATE_LIMIT`, 5xx/network/timeout → `PROVIDER_UNAVAILABLE` — all via the existing `ProviderError` model, no new categories, no raw dLocal payload or account data in any error. **`BANK_LIST` deliberately not implemented for dLocal** (dLocal's bank directory is a different endpoint; Flutterwave keeps KE bank discovery, and NG's `resolveSupportedBanks` degrades gracefully to manual bank entry). **Not yet verified against the real dLocal sandbox** — blocked on credentials (none exist); everything above is unit-tested with an injected fake HTTP client, no network.

## Payout-account verification — PROVIDER vs MANUAL (2026-09-08)

**The problem this solves, established by checking the providers rather than assuming:** Kenya has **no payment provider that can resolve a bank account**. Verified against dLocal (its account-validation endpoint documents AR/BD/CR/GH/GT/HN/IN/NG/TR/VN only — no KE), Flutterwave (NGN only; KES returns *"Invalid value 'KES' for BankAccountCurrency"*, confirmed live), Paystack (`/bank/resolve` is Nigeria + Ghana despite Kenya being a supported payments country) and Fincra (NGN/GHS/ZAR/IBAN). Root cause is structural: Nigeria has NIBSS name enquiry as an open rail every PSP resells; Kenya's equivalent sits behind PesaLink/IPSL's member banks. dLocal *does* support Kenya for payout **execution** (bank + M-Pesa wallet, Payouts v3/OAuth) — a different API, not built.

**`CountryFinancialConfig.bankVerificationMode`** (`BankVerificationMode`: `PROVIDER` | `MANUAL`, default `PROVIDER`; migration `20260908120000_payout_manual_verification`) — distinct from `bankVerificationProviderAccountId`, which says *who* verifies. This says *whether an automated verifier is expected at all*.
- `PROVIDER` — a usable bank-verification provider account is required; readiness fails without one. Unchanged behaviour.
- `MANUAL` — the vendor uploads proof of ownership and an admin verifies by hand. **A legitimate operating mode, not a gap**: `bankVerificationReasons` (`finance.readiness.compute.ts`) returns ready without looking at the binding.
- **The two paths are separate with no fallback between them** — a PROVIDER country never asks for a document (submitting one is a 400, `PROOF_NOT_REQUIRED`, never a silent ignore), a MANUAL country never calls a provider (`addPayoutAccount` uses `formatChecksProvider` directly). A failure-driven fallback is a deliberate later decision.
- Set via `PATCH /admin/v1/finance/countries/:countryRef/financial-config/bank-verification-mode` (`setBankVerificationMode`, structural scope + audited). Switching to PROVIDER without a bound account is refused (`BANK_VERIFICATION_ACCOUNT_REQUIRED`). Switching to MANUAL does **not** clear the binding — it may still serve `BANK_LIST` (the bank picker), which is independent of resolution.

**This fixed a live bug**: Kenya was `status: ACTIVE` with an ACTIVE BANK OUTBOUND method but **no** bank-verification binding, so `computeFinancialReadiness` returned `payout.ready: false` / `NO_BANK_VERIFICATION_CAPABILITY` — it would have failed its own activation gate. The only way to satisfy the old rule was to bind Flutterwave, which cannot resolve KES and would fail every real call. Kenya is now `financiallyReady: true` honestly.

**The manual method itself — copied from what marketplaces in these markets actually do, not invented.** Jumia (operating in Kenya) requires *"a stamped reference letter or 1-day statement of account"* showing the account holder's name (which must match the seller's verified legal name) and account number; the account sits **Pending Approval** (payouts blocked) until an admin approves or rejects it with a reason. Micro-deposits — the other global standard (Stripe/PayPal/Amazon) — need a working payout rail to send the deposits and so are unavailable until payout execution exists; noted as the natural upgrade.

**Deliberately not a new subsystem** — it reuses three things that already shipped:
- `DocumentScope` gained **`PAYOUT_ACCOUNT`**. The requirement is an ordinary per-country `DocumentTypeConfig` managed in the existing admin document-type UI (Kenya seeds "Bank Account Ownership Proof", `CRITICAL`, no expiry, via `payout-verification.seed.ts` — idempotent, and only flips a country to MANUAL when it has *no* provider account bound). Excluded from vendor onboarding and outlet requirements by construction: `getAllowedDocumentTypes` filters `scope: VENDOR`, the outlet resolver filters `scope: OUTLET`, and compliance detection reuses the former.
- `VendorDocument` gained a nullable **`payoutAccountId`** — a third anchor beside `applicationId`/`vendorId`, same "one row, several possible anchors" convention. Proof docs never carry `vendorId`, so they can't leak into vendor compliance listings.
- The upload is the app's one existing pipeline verbatim: `validateFile` → presign → XHR `PUT` to R2 → submit the `storageKey`. `ALLOWED_MIME_TYPES` is now exported from `vendor.document.service.ts` rather than duplicated.

`vendor.payoutProof.ts` — `getPayoutVerificationRequirement` (mode + proof type; a country with no financial config reads as MANUAL, the honest answer), `presignPayoutProofUpload`, `resolveProofForCreate`, `createProofDocument`. The rules live in a **pure `decideProofRequirement`** (`ATTACH`/`SKIP`/`NOT_APPLICABLE`/`NOT_REQUIRED`/`REQUIRED`/`WRONG_TYPE`/`MISSING_FILE`), unit-tested without a DB — same convention as `vendor.payoutRisk.ts`. The proof row is created **in the same transaction as the account**, so a MANUAL-mode account can never exist without the proof it was accepted on. Only BANK is verified this way; mobile money/wallets keep their existing structural-check + review path. Vendor routes: `GET /vendor/v1/payouts/verification-requirement`, `POST /vendor/v1/payouts/proof/presign` (refuses in a PROVIDER country).

**Everything else in the payout lifecycle is untouched** — structural checksums still gate a malformed identifier with a 400 before any row exists, encryption/blind indexes/masking, `nameMatchScore` + risk flags, PENDING/VERIFIED/FAILED/REQUIRES_REVIEW, failure codes, `getVendorGoLiveStatus`, notifications, audit. Note there is **no in-place edit endpoint** for a payout account (add/remove only), so Jumia's "only rejected accounts are editable" rule is already satisfied by construction — an approved account's number can never be swapped, only replaced by a new account that re-verifies.

**ERP**: the payout-account review page (`/finance/payout-accounts/[accountId]`) shows the proof inline with a short-lived signed `viewUrl` above the audit trail, with what to check (holder name vs legal name, bank stamp). `CountryFinancialConfigManager` gained a mode toggle.

## Bank directory follows the payout, not the verifier (2026-09-08)

`BANK_LIST` moved from the `BANK_VERIFICATION` route class to `PAYMENT_METHOD` — it now resolves through the **payout method's** provider account, not `bankVerificationProviderAccountId`.

**Why**: the bank a vendor picks becomes the stored `VendorPayoutAccount.bankCode`, and that code is later handed to whichever provider actually **moves the money**. A wrong code at verification is a recoverable annoyance; a wrong code at payout is money that doesn't move. So the directory has to come from the payout provider. The old grouping ("pick a bank from provider X's directory, then verify it with provider X") only holds when one provider does both — it breaks the moment verification and payout are separately routed, which is exactly what the capability model allows.

**It also unblocks MANUAL countries.** A MANUAL-verification country has *no* bank-verification account bound, so under the old routing `BANK_LIST` failed with `PROVIDER_ACCOUNT_NOT_CONFIGURED` and the vendor free-typed a bank name + code. Verified live against the dev DB after the change: Kenya's `BANK_LIST` now routes to **FLUTTERWAVE** (its wired BANK OUTBOUND provider, which has a KE directory) while `BANK_ACCOUNT_RESOLUTION` still correctly reports `PROVIDER_ACCOUNT_NOT_CONFIGURED`. The two bank capabilities now resolve independently, which is the point.

**Routing context is required, never guessed** — `@@unique([countryId, paymentMethodId, direction])` means a country *can* have more than one OUTBOUND BANK method, so the caller supplies it: `listSupportedBanks(vendorId, countryPaymentMethodId)` → `GET /vendor/v1/payouts/banks?methodId=`, and `assertValidPayoutMethod` validates the method is that country's, ACTIVE and OUTBOUND before it is used as routing context. Frontend: `usePayoutBanks(countryPaymentMethodId)` is keyed and gated on the chosen method, so no request fires until one is picked.

**Known follow-up, not built**: if a country's verification provider and payout provider ever use *different* bank vocabularies, the stored code will be right for the payer and wrong for the verifier. Today they agree (NG: dLocal and Flutterwave both take NIBSS codes). Translation belongs in the adapter when a real mismatch appears — deliberately not built speculatively.

**Fixed in passing**: `handleAddPayoutAccount` destructured the request body field-by-field and never included `proofDocument`, so the MANUAL-mode proof was silently dropped before reaching the service. Now passed through.

## Payout storage layout, one destination, in-page proof review (2026-09-09)

A cleanup pass after the manual-verification work went in. Migration `20260909120000_payout_account_reviewer`.

**R2 layout for payout proofs.** New `R2Service.generatePayoutProofKey` → `payout-docs/<method>/<vendorId>/<uuid>.<ext>` (`bank-account` / `mobile-money` / `digital-wallet` / `card`, from `payoutProofFolder(methodType)` in `vendor.payoutProof.ts`). Deliberately different from `generateStorageKey`, which stays exactly as-is for application/account/outlet documents — changing that prefix would orphan every object already uploaded under it.
- Keyed on the **vendor account id**, not `vendorUserId` — a payout account belongs to the business and that's the id every admin surface shows.
- **Not country-scoped**, matching vendor application documents (the vendor id already implies the country).
- No `documentTypeId` segment — the method folder already says what the document is, keeping the path short.
- Folder is keyed on the method **type** (a closed enum), not the per-country method name: M-Pesa and Airtel Money are both `MOBILE_MONEY` and belong together rather than fragmenting the prefix per network.
- Filename stays a **uuid**, deliberately not a fixed `document.pdf`: a rejected account is re-submitted with a new proof and every `VendorDocument` row is versioned rather than overwritten — a fixed name would silently destroy the evidence a manual decision rests on.
- The presign now requires `countryPaymentMethodId` (it decides the folder) and validates it through `assertValidPayoutMethod` first, so a method id from another country can never steer the key.

**One payout destination, several accounts on file.** This matches how marketplaces actually work — Stripe Connect's `default_for_currency`, Jumia's "preferred payment instrument"; Uber Eats/DoorDash present the same model with the list hidden (one bank account per store, replaceable). The `isDefault` machinery already existed; two real gaps were closed:
- `addPayoutAccount` set `isDefault: existingActive === 0` — the **first** account became the destination even while `PENDING`, silently bypassing the `ACCOUNT_NOT_VERIFIED` guard `setDefaultPayoutAccount` enforces. Now `existingActive === 0 && verificationStatus === VERIFIED`.
- `verifyPayoutAccount` promotes the account to default when the vendor has none — otherwise a vendor whose accounts were all unverified would have no destination until they happened to press "set default".
- New `resolvePayoutDestination(vendorId)` (`vendor.payout.service.ts`) — the single "where does the money go" resolver every future payout run must call. Returns null (never a guess) when there's no verified active account or the vendor is on `payoutHoldStatus: HELD`.

**Reviewer recorded on the row.** `VendorPayoutAccount.reviewedById`/`reviewedAt`, mirroring `VendorApplication.reviewedById`/`reviewedAt`. Both `verifyPayoutAccount` and `rejectPayoutAccount` set them — **reject previously recorded nobody on the row at all**, so "who turned this down?" was only answerable by reading the audit log. Distinct from `verifiedBy`/`verifiedAt`, which still mark the moment it *became* verified. The detail response resolves the id to a name and the page shows a "Reviewed by" row.

**Proof review happens in-page.** `PayoutProofSheet` (shadcn `Sheet`, right side, `sm:max-w-3xl`) replaces the new-tab link on `/finance/payout-accounts/[accountId]` — PDFs in an `<iframe>`, images in an `<img>`, both off the existing short-lived signed R2 URL. The approve/reject decision is made on that page against the masked account number, holder name and bank code, so sending the reviewer away to read the evidence was the wrong shape. An "Open in a new tab instead" escape hatch remains, since some browsers refuse to frame a PDF.

## Payout-account review workflow — claim / escalate / reassign (2026-09-09)

Payout-account review brought to full parity with the application / appeal / compliance-case queues, at the user's direction. Migrations `20260909140000_payout_review_workflow`, `20260909150000_payout_review_notifications`.

**Mirrors `admin.vendor.appeal.service.ts` function-for-function** (which itself mirrors `admin.vendor.compliance-case.service.ts`, the most refined version) rather than the older, looser applications pattern — same rules, same error codes, same audit shape, so an admin who has worked either queue already knows this one. New `admin.payoutReview.service.ts`.

**Why payout gets this machinery when profile moderation deliberately doesn't**: a payout decision routes real money to a real bank account. Two admins acting concurrently is a genuine race with financial consequences, not the non-event two admins approving the same profile flag would be.

**The two hand-offs are different actions** — this is the answer to "does the reviewer pick a target, or is it a free pool?". The codebase already does **both**, and payout now matches:
- **Escalate** — free pool. Clears the assignee, sets `escalatedByAdminId`/`escalatedAt`/`escalationReason`, notifies every in-country `VENDORS_PAYOUT_ACCOUNTS_RECEIVE_ESCALATION` holder (`PAYOUT_ACCOUNT_ESCALATED`). Whoever is free claims it. Refuses up front if nobody in-country could ever receive it (`NO_ESCALATION_RECEIVER`), pointing at reassign instead.
- **Reassign** — targeted. Names the receiving admin, does NOT require the actor to hold the claim (supervisory override), notifies the target (`PAYOUT_ACCOUNT_ASSIGNED`). Reassigning *out of* the escalation pool narrows eligible targets to escalation receivers only.

Rules carried over verbatim: the escalating admin is permanently locked out of that account (`ESCALATED_BY_YOU`); `claimedFromEscalation` is terminal — an admin who claimed straight out of the pool must decide directly and cannot escalate again, while a *reassigned* admin has it reset to `false` and may; escalation-pool claims are country-scoped only (a global admin cannot self-claim out of the pool); the claim itself is an atomic `updateMany` guarded on `assignedReviewerId: null`, so two simultaneous claims are resolved by the database.

**verify/reject now REQUIRE the claim** (`assertPayoutReviewClaimedByActor`) — no "unclaimed = anyone may act" fallback, the same rule `resolveAppeal` and the compliance waive/notify/revoke actions already enforce. This is the point of the workflow: exactly one owner when money is decided.

**No new status enum — the workflow state is DERIVED** (`admin.payoutReview.state.ts`, pure + unit-tested): `UNCLAIMED` / `CLAIMED` / `ESCALATED` / `RESOLVED` from `assignedReviewerId` + `escalatedAt` + `verificationStatus`. `VendorAppeal` and `VendorComplianceCase` each carry their own status enum because they have no other notion of "done"; a payout account already has one, and a second enum would give "is this resolved?" two sources of truth that could disagree. The one trap the tests pin down: `escalatedAt` persists as history after a reassignment, so `ESCALATED` must mean *escalated **and** nobody holds the claim* — otherwise an owned account would stay stuck in the escalation queue.

**Permissions** (`vendor_ops` pool, synced to `super_admin`): `VENDORS_PAYOUT_ACCOUNTS_CLAIM` / `_ESCALATE` / `_REASSIGN`, plus `_RECEIVE_ESCALATION` as a **ceiling-only** entry granted individually to senior reviewers — same pattern as every other `RECEIVE_ESCALATION`. Routes: `POST /admin/v1/finance/payout-accounts/:id/{claim,release,escalate,reassign}`, `GET …/eligible-targets`.

**Audit** — every action goes through the existing `auditService`: `vendor_payout_account.review_claimed` / `_released` / `_escalated` / `_reassigned`, alongside the pre-existing `.verified` / `.rejected`. Combined with `reviewedById`/`reviewedAt` on the row, both "who decided this" and "how it got to them" are answerable without reading the audit trail — and the full trail is still there.

**Frontend**: `PayoutReviewActions.tsx` (claim / release / escalate / reassign, same `AlertDialog` shape as `ComplianceIssueActions` — Reassign reads "Assign" until the account has ever been claimed), plus a workflow bar on `/finance/payout-accounts/[accountId]` showing who holds it and any escalation reason.

**`/finance/payout-accounts` list cleanup (2026-09-09).** Server-side pagination already existed (`listVendorPayoutAccounts` takes `page`/`pageSize`); the page now asks for **10** rows instead of 20. Reason and Added columns moved to the detail page and replaced by an explicit **View** button — the list is a queue, and one obvious way in beats a row that is subtly clickable in two places.

**"Search returns nothing" was not a broken search.** Search is ANDed with the status tab, which defaults to the *Requires review* work queue (same convention as `/vendors/compliance` and `/vendors/profiles`). With the only payout account sitting at VERIFIED, every search legitimately returned zero. Verified against the dev DB: `search="Manu"` + `status=REQUIRES_REVIEW` → 0 rows, while the same search across all statuses → 1. Fixed properly rather than by changing the default: the per-status **counts are now search-aware** (`countWhere` carries the same `searchOr` predicate as the row query), so when a search finds nothing in the current tab the empty state names how many matched elsewhere and offers a one-click "Search all statuses". A search that genuinely matches nothing still shows the plain empty state.

## Vendor setup / go-live gating — Uber Eats model (2026-09-08)

**Three tiers, and payout verification only touches the third.** Copied from Uber Eats / DoorDash / Bolt Food, which all let a merchant build their menu *during* onboarding while banking is pending (Jumia likewise: bank approval blocks *payments being sent*, not listing; Stripe Connect keeps `charges_enabled` and `payouts_enabled` as separate flags).

1. **Access** — dashboard, settings, documents, notifications. Gated on *not banned* (`v1Router.use(requireVendorState(...NON_BANNED_STATES))`).
2. **Authoring** — profile, outlets, payout, documents, **meals, meal plans**. Gated on account `ACTIVE` only (`requireSetupAccess` / `requireVendorState("ACTIVE")`).
3. **Commercial activation** — publish storefront, orders, subscriptions. Gated on `getVendorGoLiveStatus().canGoLive`, which includes `hasVerifiedPayoutAccount`.

**Fixed here**: `meals` and `meal-plans` were under `app/(dashboard)/(operational)/`, whose layout calls `requireOperationalAccess()` → `canGoLive` → verified payout. A vendor genuinely could not build a menu until their bank account was verified — with manual review at 2–3 days, that idles them at exactly the wrong moment. Both moved to a new `app/(dashboard)/(authoring)/` group gated on `requireSetupAccess()`. `orders`/`subscriptions`/`dashboard` correctly stay operational. `nav-links.ts` now splits `authoringNavItems` from `operationalNavItems`; a not-live vendor sees Meals/Meal Plans/Setup, a live one sees everything. A `NotLiveBanner` renders the authoritative `blockers[]` across the dashboard (never re-deriving readiness) so "why can't customers see me?" is always answered on screen.

**`/setup` is no longer a second app shell (same pass).** It had its own `app/setup/layout.tsx` + `SetupNavbar` + `SetupFooter` — no sidebar, separate chrome. That only became actively confusing once a not-live vendor could *also* be in the dashboard building their menu, bouncing between two chromes. Every merchant platform being modelled here has exactly **one** shell — Uber Eats Manager, DoorDash Merchant Portal, Shopify and Jumia Vendor Center all treat setup as a **checklist, not a place**, with its destinations living permanently under Settings. So `app/setup/*` moved to `app/(dashboard)/(setup)/setup/*` (a sibling ACTIVE-gated group to `(authoring)`; `SetupNavbar`/`SetupFooter` deleted). **Every URL is unchanged** — route groups don't appear in the path — so no links, bookmarks or redirects broke.

Nav follows the same shape: **Setup** (the checklist) appears only while not selling-ready and disappears once live, exactly like Shopify's setup guide; **Settings** is a permanent dropdown (Payout / Public profile / Locations / Documents) present in *both* tiers, because changing a bank account or adding a location is ongoing business configuration, not a one-time onboarding step. The `/setup` page itself still exists for anyone who navigates to it. Renaming the URLs to something like `/settings/payout` is a cosmetic follow-up with real link churn and no behavioural value — deliberately not done.

Deliberately unchanged: onboarding gating stays as-is (it gates because the vendor *isn't a vendor yet* — identity and documents unproven; once approved that's settled, and a payout account is a financial routing detail discovered later). Meal-plan *offering* keeps its own finer gate (`getOutletMealPlanReadiness`); only *authoring* moved.

**ERP (`/countries/[slug]/finance`, `CountryFinancialConfigManager.tsx`):** no "primary provider" concept. Provider accounts list shows each account's capabilities, its per-account currency-support flag (`currencySupported`), and a "bank verification" marker on the one bound for that capability (`ProviderAccountActions` → "Use for bank verification" / "Stop using…", `PATCH …/financial-config/bank-verification-account`). Collection/payout routing is the per-method wiring table. Readiness reasons are rendered from the backend, never re-derived. Currency is read-only ("owned by the country").

**Finance ↔ Payments boundary (Payments module does not exist yet):** Finance owns provider config, routing, credentials, readiness, adapters, and (for now) webhook ingestion. When Payments is built it takes payment-intent/attempt/capture/refund orchestration + webhook→state reconciliation + `ProviderWebhookEvent`; Finance keeps the provider *contract* (the adapter capability interfaces) and never grows a `createCharge`/`createPayout` service.

**Deferred (unchanged by this pass):** payout execution, Payments module, ledger, settlement/reconciliation, treasury/intercompany, legal-entity + settlement-bank-account models, courier payouts, generic webhook route, dLocal collection/payout rails (only its account-validation capability is built), dLocal countries beyond Nigeria (a one-line `DLOCAL_ACCOUNT_VALIDATION` entry each), live dLocal sandbox verification (blocked on credentials), automatic→manual verification fallback (deliberately excluded — the two paths stay separate until there's a reason), micro-deposit verification (needs a payout rail), mobile-money account verification (no provider offers M-Pesa name lookup; stays structural-check + review). Legacy `CountryPaymentMethod.verificationProvider`/`verificationConfig`/`ourAccountDetails` (pre-abstraction, grep-confirmed unused) and the `Country.currency` string migration are known cleanup, not touched here.

## Vendor-dashboard route flattening + outlets list (2026-09-09)

`apps/vendor-dashboard` had five route groups — `(auth)`, `(dashboard)`, and three *nested* inside it: `(authoring)`, `(operational)`, `(setup)`, each with its own layout whose only job was calling one guard. Collapsed to **`(auth)` + `(dashboard)` only**. Every page now calls its own guard (`requireSetupAccess()` / `requireOperationalAccess()`) as its first statement, so a route's access rule is visible in the file that defines the route rather than in an ancestor layout three directories up. The gating itself is unchanged — the same two guards, applied to the same pages.

**URLs changed** (unlike the earlier `/setup` shell move, which was group-only and left paths intact):

| before | after |
|---|---|
| `/setup/payout` | `/settings/payouts` |
| `/setup/profile` | `/settings/profile` |
| `/setup/documents` | `/settings/documents` |
| `/setup/outlets`, `/setup/outlets/[id]`, `/setup/outlets/create` | `/outlets`, `/outlets/[id]`, `/outlets/create` |

`/setup` itself stays — it's the checklist, and the nav still shows it only until the vendor is selling-ready. Outlets moved out of `/settings` on purpose: locations are a business surface a vendor works in daily, not a settings page. Every inbound link was rewritten (`nav-links.ts`, `lib/readiness.ts`, `OutletGoLivePanel`, `OutletCard`, `CreateOutletForm`); no redirects were added, since the app is pre-launch and nothing external links to these paths.

**`lib/vendor/outlets.ts` — the one place vendor outlet endpoints are called.** The outlet pages previously hand-rolled `fetch(`${BACKEND}/vendor/v1/outlets/`)` with a raw Clerk token, bypassing `backendFetch` and its error envelope entirely. Now `getOutlets` / `getOutletCities` / `getOutlet` go through `backendFetch` with `revalidate: 60` + tags (`vendor-outlets`, `vendor-outlet-<id>`). **Caching per-vendor data this way is safe, verified not assumed**: Next hashes the request headers into the Data Cache key (`IncrementalCache.generateCacheKey`), so the bearer token is part of the key and one vendor can never read another's cached response — the TTL is what stops a rotating Clerk token piling up entries. `getOutlet` turns a 404 into `null` (→ `notFound()`) and rethrows everything else.

**Fixed in passing**: `backendFetch` overwrote `next` when `revalidate` was passed, so a caller passing both `revalidate` and `tags` silently lost the tags — meaning `revalidateTag` would never have invalidated those reads. Both are now merged into one `next` object.

**Server-side outlet list.** `listOutlets(vendorId, { search, status, cityId, page, pageSize })` (`vendor.outlet.service.ts`) is now paginated and filterable (search over name + address line 1, `adminStatus`, city), returning `{ outlets, total, page, pageSize }`; new `listOutletCities(vendorId)` returns only the cities the vendor actually has outlets in, so the filter can't offer a choice that matches nothing. New route `GET /vendor/v1/outlets/cities`, registered **before** `/:id` so the literal segment wins.

**Page shape — short SSR pages, components own the markup.** The outlet detail page was 232 lines of inline JSX; it's now ~55, delegating to `OutletDetailHero`, `OutletEditSections` and `OutletFlagNotice`. The list page delegates to `OutletFilterBar` (the only client component — it writes the query string, the filtering is entirely server-side) and `OutletsEmptyState` (which distinguishes "no outlets yet" from "no outlets match these filters"). New shared `ListPagination` (`components/dashboard/layout/`) is deliberately link-based, not a client component: every list page here is an SSR page reading `searchParams`, so page changes need no JS. `isNavActive` (`nav-links.ts`) is now the one place a nav link decides it's current — prefix-with-trailing-slash, so `/outlets` stays lit on `/outlets/create` while `/meals` correctly does not light up on `/meal-plans`.

**Two deliberate deviations from the literal request, both flagged:**
- **No `/profile/create` + `/profile/update` split** — the backend is a single `upsertVendorProfile` (full-form save, not partial PATCH). Two routes rendering the same form against the same operation is duplication, which contradicts the DRY instruction that came with the request. One page, `/settings/profile`.
- **`/outlets/revenue` is an honest placeholder, not a chart.** There is no `Order` or `Payment` model in the schema, so every figure would be invented. Mock revenue is acceptable in an internal admin tool (and is used there); showing a *vendor* fabricated earnings for their own business is not. The route and page exist so the real report drops in once orders are captured.
